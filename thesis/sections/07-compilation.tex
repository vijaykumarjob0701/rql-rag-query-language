\subsection{Established adapter surface survey (docs-only, Sep 2026)}
\label{sec:vendor-matrix}
A docs-only survey of public vendor APIs (journal 0020; companion package \texttt{docs/09-vendor-api-matrix.md}; OKF \texttt{knowledge/reads/vendor-api-matrix-2026-09/}) records, without live cluster calls:

\begin{itemize}
  \item \textbf{Filter DSLs} differ (Qdrant JSON \texttt{Filter}; ES/OS Query DSL; Weaviate \texttt{where}; Milvus \texttt{expr}; pgvector SQL \texttt{WHERE}).
  \item \textbf{Filter$+$ANN composition} is not uniform: Weaviate documents pre-filtering; Elasticsearch documents \texttt{knn.filter} during approximate kNN; pgvector documents post-filter on approx indexes plus iterative scans ($\geq$0.8.0); Milvus API text states expr before ANN; Qdrant emphasises leaf filter propagation; Redis documents hybrid \texttt{BATCHES}/\texttt{ADHOC\_BF} modes.
  \item \textbf{RRF} is first-class in Qdrant (\texttt{rrf}), Elasticsearch (\texttt{retriever.rrf}), OpenSearch (score-ranker RRF), and Milvus (\texttt{RRFRanker}); Weaviate exposes \texttt{rankedFusion}; pgvector/Pinecone often require client/SQL shims.
  \item \textbf{Weighted / score fusion} appears as Milvus \texttt{WeightedRanker}, Weaviate \texttt{relativeScoreFusion}+\texttt{alpha}, Qdrant \texttt{dbsf}/formula, ES boosts/weighted RRF---semantics are \emph{not} interchangeable.
  \item \textbf{Multi-vector / late interaction} is documented for Qdrant multivector rescore and Weaviate multi-vector (ColBERT-style); elsewhere often \textbf{UNKNOWN} or nested dense only.
  \item \textbf{EXPLAIN / plan visibility}: PostgreSQL \texttt{EXPLAIN} (pgvector) and ES Profile / OpenSearch hybrid score explanation are clearly documented; several others remain \textbf{UNKNOWN}, so RQL \texttt{EXPLAIN} will often be adapter-synthesised.
\end{itemize}

\noindent URLs and UNKNOWN cells are cited in the package matrix; this section does not invent undocumented APIs \established{} as a \emph{surface survey}.

\subsection{Substrait / Calcite IR adjacency}
\label{sec:substrait-calcite-adjacency}
\noindent\textit{Source facts below are \established{} from Substrait docs (accessed 2026-09-17) and Begoli et al.~\citep{begoli2018calcite}; Cascades~\citep{graefe1995cascades} is cited for optimizer vocabulary.
RQL packaging remains \hypothesis{} adjacency---\textbf{not} a Substrait implementation or Calcite embedding (journal 0025).}

\paragraph{Established prior systems.}
Substrait~\citep{substrait} is an open, cross-language specification for \emph{serialized relational/compute plans} (binary protobuf and text), complementary to SQL: producers and consumers exchange plans rather than SQL text.
Plans are trees of relations (DAGs via reference relations) with emit/ordering, optional hints and constraints, and distribution/orderedness properties.
The specification does \textbf{not} enforce a hard logical/physical split---operators such as hash join, exchange, and top-$N$ are conventionally physical; the consuming system decides what counts as a physical plan.
Extension points include YAML simple extensions (types and functions via extension URNs), \texttt{AdvancedExtension} (ignorable \emph{optimization} hints vs semantic \emph{enhancements}), and custom \texttt{ExtensionLeafRel}/\texttt{ExtensionSingleRel}/\texttt{ExtensionMultiRel} relations whose detail schemas are producer/consumer agreements.

Apache Calcite~\citep{begoli2018calcite} is an embeddable relational algebra and optimizer framework over heterogeneous sources: SQL parser or \texttt{RelBuilder} yields a tree of relational operators; pluggable rules, metadata providers, and planner engines rewrite that tree; adapters expose external schemas and push operators into backend \emph{calling conventions}.
Physical properties are modeled primarily as \textbf{traits} (ordering, partitioning, calling convention) rather than a mandatory dual logical/physical operator class hierarchy; an \emph{enumerable} convention supplies iterator-based client operators when a backend cannot execute an op.
Calcite's cost-based engine uses Volcano-like dynamic programming over equivalence sets~\citep{begoli2018calcite}; Cascades~\citep{graefe1995cascades} supplies classic vocabulary (task-based search, memoization, property \emph{enforcers}) behind many ``Cascades/Volcano-style'' citations.

\paragraph{Hypothesis: RQL is inspired-by, not identical.}
We \hypothesis{} that RQL's draft \texttt{LogicalPlan}/\texttt{PhysicalPlan} JSON (\texttt{0.1.0-draft}; journal 0021) and capability-negotiated compile stack (journals 0022--0024, 0026) are \emph{Substrait-inspired} (portable plan IR; domain ops as future extension relations; adapters as plan consumers) and \emph{Calcite-inspired} (algebra tree + physical strategies via capability/trait negotiation; pushdown vs explicit \texttt{ShimCast} fallback).
Honest non-claims: RQL does \textbf{not} implement Substrait protobuf wire compatibility; is \textbf{not} a Calcite extension or \texttt{VolcanoPlanner}; and journal~0023 is \textbf{not} a Cascades cost model.
A future retrieval-oriented Substrait dialect (custom relations for $\mathrm{Search}_{late}$ / $\mathrm{Fuse}_{rrf}$ / FANNS filter modes) remains optional future work---not claimed done here.
